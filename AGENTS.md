# AGENTS

## Правила разработки (обязательно)

### Git и production-выкладка
- Любые изменения для production сначала фиксировать коммитом и отправлять в соответствующий remote. Перед выкладкой проверять успешный push и совпадение локального HEAD с удалённой веткой во всех участвующих репозиториях.
- Не выкладывать рабочие незакоммиченные файлы. На сервере проверять точную ревизию релиза; после выкладки сверять её с запушенным коммитом и фактически запущенной сборкой.
- Для изолированной поставки файлов из другого репозитория (например Airpay Hub) собирать архив только из конкретного запушенного коммита, сохранять manifest с ревизией и контрольными суммами и проверять файлы на сервере. Не заменять рабочие модули Interhub ради синхронизации репозитория.
- Записи о результате выкладки также коммитить и пушить. В итоговом ответе указывать ревизии, что выложено и результаты проверок; Git должен оставаться актуальным.

### Миграции БД
- Любое изменение схемы PostgreSQL (`CREATE/ALTER/DROP TABLE`, колонок, индексов, constraint, схем) добавлять только новым SQL-файлом в `db/migrations/runtime/`.
- Не выполнять DDL из `api/app.py`, lifespan/startup-кода, API-обработчиков, фоновых задач и импортов. API работает только с уже подготовленной схемой.
- Исторические файлы в `db/migrations/` не изменять и не запускать повторно: мигратор фиксирует их как базовую линию. Новые миграции именовать по шаблону `YYYYMMDD_NN_краткое_описание.sql`.
- Для индексов на рабочих таблицах использовать `CREATE INDEX CONCURRENTLY` и первой строкой файла ставить `-- migrate:no-transaction`.
- Не добавлять в обычные миграции `DROP TABLE`, `TRUNCATE`, массовый `DELETE` или необратимое изменение данных. Такие операции требуют отдельного согласования, резервной копии и плана отката.
- Перед перезапуском API сначала запускать мигратор. Для staging: `sudo -n docker compose -f docker-compose.staging.yml --env-file .env.staging --profile maintenance run --rm --build migrate`.
- После миграции проверять запись в `app.schema_migrations`, `/health`, логи API/PostgreSQL и ключевой пользовательский сценарий. В production перед первой миграцией обязательно проверять резервную копию.

### Подключение к staging БД по запросу пользователя
- Если пользователь просит подключиться к тестовой БД, использовать только staging SSH-туннель из VS Code-задачи: `ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:5433:127.0.0.1:5433 adminops@138.16.162.73`.
- Подключение приложения и мигратора брать из `.env.dev`; оно указывает на `127.0.0.1:5433/gamesales_staging`. Не выводить DSN, пароль, токены или другие секреты в терминал и ответы.
- Открывать туннель только для согласованной диагностики или миграции staging и после завершения обязательно закрывать именно созданный/подтвержденный процесс, проверив, что порт `127.0.0.1:5433` больше не слушается.
- Не применять миграции и не подключаться к production без отдельного явного запроса пользователя.

### Definition of Done для изменений фронта
- Если меняется логика в `gamesales-web/src/views/work/**`, нужно обновить существующие тесты или добавить новые `*.vitest.test.js`.
- После любых изменений запускать: `cd gamesales-web && npm run check`.
- Задача считается завершенной только если `npm run check` проходит без ошибок.

### Комментарии в коде
- В новых и измененных функциях добавлять короткие комментарии на русском языке простыми словами.
- Комментарий должен отвечать на вопрос "что делает этот блок и зачем".
- Не писать очевидные комментарии вида "переменной присвоено значение".

### Рефакторинг и декомпозиция
- При выносе логики из крупных файлов не терять текущее покрытие тестами.
- После выноса в новый модуль переносить/добавлять тесты на этот модуль.
- Найденные техдолги и отложенные улучшения добавлять в `TODO.md`.

### Стабильность UI
- После изменений, связанных с модалками, фильтрами, таблицами и стилями, ручной smoke-check экрана `WorkView` выполняет пользователь. Агент не открывает локальный интерфейс или браузер для такой проверки без прямого запроса пользователя.
- Если стиль "уехал" после рефакторинга, сначала проверять порядок и область подключения CSS, затем вносить правки.
