# CONTRIBUTING

Короткие правила разработки для этого репозитория.

## Обязательные правила

1. Комментарии в коде:
- Добавляем короткие комментарии простым языком (по возможности на русском), когда логика неочевидна.
- Не пишем комментарии на каждую строку; только там, где это реально помогает понять код быстрее.

2. Тесты при изменениях:
- Любой новый функционал должен идти с тестами.
- Любой рефакторинг, который затрагивает поведение, должен обновлять/добавлять тесты.
- Если тестов нет, сначала добавляем минимально достаточные тесты и только потом продолжаем рефакторинг.

3. Перед завершением задачи запускаем проверки:
- Frontend: `cd gamesales-web && npm run check`
- Backend: `cd api && make test-pytest` (или `make test-v`, если pytest недоступен)

4. Миграции БД:
- Любое изменение схемы PostgreSQL (`CREATE/ALTER/DROP TABLE`, колонок, индексов, constraint, схем) добавляем только новым SQL-файлом в `db/migrations/runtime/`.
- Не выполняем DDL из startup/lifespan-кода, API-обработчиков, фоновых задач и импортов: API работает только с уже подготовленной схемой.
- Исторические файлы в `db/migrations/` не изменяем и не запускаем повторно. Новые миграции именуем `YYYYMMDD_NN_краткое_описание.sql`.
- Для индексов на рабочих таблицах используем `CREATE INDEX CONCURRENTLY`; первая строка такого файла — `-- migrate:no-transaction`.
- Обычные миграции не должны содержать `DROP TABLE`, `TRUNCATE`, массовый `DELETE` или необратимое изменение данных. Для таких операций нужны отдельное согласование, проверенная резервная копия и план отката.
- До перезапуска API запускаем мигратор, затем проверяем `app.schema_migrations`, `/health`, логи API/PostgreSQL и основной пользовательский сценарий.

## Чеклист перед merge

- [ ] Код читаемый, сложные места прокомментированы.
- [ ] Тесты добавлены/обновлены под изменения.
- [ ] Все локальные проверки проходят.
- [ ] Для изменения схемы создана миграция в `db/migrations/runtime/`, а DDL не добавлен в API.
