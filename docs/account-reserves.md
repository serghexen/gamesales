# Резервы аккаунтов

## Хранение

`account_reserve_codes.reserve_id` — постоянный ID конкретного кода. Пара
`account_id + reserve_key` является его неизменяемым адресом для существующего API и
связей `deal_items`. Номер `reserveN` не используется повторно даже после удаления
значения. Значение до завершения выдачи хранится в `account_secrets`; SHA-256 отпечаток
остаётся для обнаружения попытки повторно добавить уже списанный код.

Редактор отправляет список значений и исходный снимок `expected_reserves`. Сервер
сопоставляет неизменённые значения, выдаёт новым значениям новые ID и отклоняет
устаревший снимок с HTTP 409. Перестановка не меняет ID. Удаление из списка скрывает
код через `is_listed`, сохраняя его для прежней сделки. Одиночные старые API и импорт
используют тот же сервис; они не перезаписывают содержимое существующего резерва.

## Выдача

Редактирование, импорт, выбор и копирование сериализуются блокировкой строки
аккаунта. Редактирование сделки также блокирует саму сделку. Перенос между аккаунтами
блокирует аккаунты в порядке ID.

Кнопка копирования всегда проходит серверную проверку. Для существующей сделки
сервер проверяет реальную сохранённую связь с кодом. Другой выбранный код требует
обычного claim. Свой незавершённый claim можно выбрать и привязать к сделке, в том
числе после копирования из аккаунта или потери ответа сервера. Повторный claim
идемпотентен и не откатывается ошибкой параллельного копирования.

Создание и обновление черновика используют одинаковое назначение. Явно выбранный
занятый/отсутствующий код даёт HTTP 409, без автоматической подмены. Просмотр старой
сделки не подбирает новый код. Пользователь может явно выбрать резерв в новой или
редактируемой незавершённой сделке. Пустая строка означает отсутствие назначения;
для старого клиента без поля при создании допустим автоматический выбор.

При выборе аккаунта в редактируемом черновике форма подставляет первый свободный
резерв после загрузки точной занятости. Это действует и для дубля, и если статус
«В ожидании» выбран раньше аккаунта в той же открытой форме черновика. До окончания
подбора сохранение заблокировано. Подстановка не заменяет уже выбранный или
скопированный код; закрепление в БД происходит при сохранении сделки.
Открытие карточки, включение редактирования и просмотр завершённых сделок ничего
не назначают. Ответы после закрытия или смены сделки не меняют выбор.

Редактор аккаунта отправляет `reserve_values` и `expected_reserves` только при
изменении содержимого поля резервов. Пробелы и перестановка тех же кодов не требуют
перезаписи. Сохранение деактивации, комментария или пароля не заменяет неизменённые
резервы, другие секреты и привязки товаров. При настоящей замене или очистке списка
сервер по-прежнему проверяет исходный снимок и возвращает конфликт без автоповтора.

При каждом открытии карточки секреты и товары загружаются заново; редактирование
и сохранение ждут успешной загрузки. Ошибка не очищает кеш и не считается пустым
списком. После ошибки можно повторить «Обновить из базы». Запоздалые ответы не
переписывают свежий кеш и повторно открытую карточку. Переход из сделки использует
ту же загрузку. Частичный успех отдельных запросов сохранения показывается явно;
после успешной записи секретов исходный снимок обновляется для безопасного повтора
оставшихся изменений. Общая атомарная API-операция остаётся в TODO.

Отмена освобождает только нераскрытый код. После копирования состояние выдачи
сохраняется независимо от удаления/переноса сделки. Незакреплённые выданные коды
не возвращаются в свободные по таймеру.

## Завершение

При переходе в `completed` удаляются значения закреплённых резервов и прежних
выдач из истории этой сделки, а также их claims; ID, отпечаток и журнал событий остаются. Изменение статуса и удаление
выполняются одной транзакцией. Повторное завершение не списывает следующий код.
Если старый код связан с другой незавершённой сделкой, значение сохраняется до
завершения последней такой сделки. Это защита от исторических дублей связей.

В завершённой сделке поле содержит только **выдан**, без значения, пояснений и
кнопки копирования. Возврат сделки в работу не восстанавливает удалённый код;
новую выдачу выбирают явно. Исторический импорт завершённых слотов не назначает
и не списывает текущие свободные резервы аккаунта.

## Миграция и выкладка

Нужна `20261026_01_account_reserve_identity.sql`. Она добавляет метаданные и журнал,
не удаляя существующие коды. Старые связи и claims сохраняются; связанные со
старыми сделками коды консервативно считаются уже раскрытыми, поскольку прежний UI
позволял копирование без claim. Уже завершённые сделки не запускают массовое
удаление при миграции. Точное восстановление значений, заменённых до этой миграции,
требует отдельного аудита исторических данных.

Перед production нужны резервная копия, согласованное окно остановки старых
писателей, запушенные ревизии и запуск мигратора до нового API. Одновременно
эксплуатировать старый API, напрямую пишущий reserveN, и новый сервис нельзя.
После первых записей нового механизма возврат старого API без согласованного
восстановления данных небезопасен: старый код может снова перезаписывать ID.

Проверка после применения: запись миграции, `/health`, логи и сценарии замены
занятого кода, копирования, сохранения черновика, завершения и повторного открытия.
Конкурентные claim/create/update нужно проверить на PostgreSQL с отдельными
соединениями. Unit-тесты сервиса используют изолированный SQL-движок в памяти и
не доказывают поведение блокировок PostgreSQL. Ручной smoke WorkView выполняет
пользователь согласно AGENTS.md.

Production-выкладка и проверки 27.10.2026 зафиксированы в
[отчёте о релизе](account-reserves-release-20261027.md). Интеграционные проверки
`api/tests/test_account_reserves_postgres_unittest.py` принимают только явно заданный
`GAMESALES_RESERVES_TEST_DSN` с именем отдельной восстановленной БД
`gamesales_reserves_test`; они не предназначены для production.
