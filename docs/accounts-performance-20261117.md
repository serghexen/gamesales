# Диагностика вкладки «Аккаунты» — 17.11.2026

Последующее обновление: [профилактика внедрена на production](statistics-maintenance-release-20261117.md).
Ниже сохранены исходные замеры и результаты последовательных этапов диагностики.

Production проверен с разрешения пользователя только чтением. Ревизия сервера
и локального репозитория: `e218c3c235bd5669d95fd8757b5eb90d4908e789`.
SHA256 работающего `accounts_api.py` совпал с локальным:
`5d1c13ce43ee62e1a069e60cd77a98e976497b3b95d097d21528d6ac78db6e98`.

## Замеры

- В авторизованной Safari-сессии при переходе со «Сделок» на «Аккаунты»:
  запрос accounts — HTTP 200, 4,43 с, передано 1,52 КБ. Таблица загрузилась.
  Это время сетевого запроса, не отдельный замер от клика до отрисовки.
- После списка наблюдались 20 запросов secrets (145–368 мс каждый) и
  20 reserve-usage (132–199 мс каждый). Параллельные длительности не суммируются.
- Точный SQL работающего обработчика, первая страница, 20 аккаунтов,
  сортировка login asc, без пользовательских фильтров: 4363,50 / 4312,90 /
  4784,19 мс. Получены 80 строк слотов для 20 аккаунтов, total = 5221.
- EXPLAIN (ANALYZE, BUFFERS): выполнение 4677,143 мс, планирование 10,263 мс.
  JIT: 4398,214 мс, около 94% времени выполнения; оптимизация 2513,528 мс,
  генерация машинного кода (Emission) 1714,834 мс. Чтений shared blocks с диска
  и временных записей в этом прогретом плане не было.
- В отдельной REPEATABLE READ READ ONLY транзакции: исходный запрос 4063,16 мс;
  после SET LOCAL jit=off — 218,20 / 257,22 / 337,88 мс. Все возвращённые
  строки и порядок полностью совпали с исходным запросом на том же снимке.
  EXPLAIN без JIT: выполнение 289,241 мс, планирование 8,726 мс.

## Причина и границы выводов

В БД 5229 аккаунтов и 24740 назначений слотов, из них 18814 активных.
Главная измеренная задержка связана с JIT, а не передачей большого ответа.

Для app.slot_types pg_class показывает reltuples=-1, relpages=0, а
pg_stat_user_tables — last_analyze и last_autoanalyze NULL. План оценивает
510 строк при фактических 4; вложенное соединение с аккаунтами оценивается
в 2631090 строк вместо примерно 21 тысячи. Стоимость всего плана 656648,7
превышает пороги JIT: 100000 для включения и 500000 для inlining/optimization.
Отсутствие статистики — конкретный фактор завышенной оценки; эффект ANALYZE
пока не проверялся, поскольку он меняет статистику production.

В SQL есть агрегации до LIMIT и две ссылки на представление слотов.
Однако для проверенного обычного открытия планировщик исключил ненужную
агрегацию account_slots_agg. Нельзя утверждать, что обе ссылки всегда
выполняются или что именно двойной расчёт слотов вызвал эти четыре секунды.
Оставшийся план всё ещё агрегирует слоты примерно для всей базы.

## Предлагаемый порядок улучшений

1. После разрешения на обслуживание выполнить точечный ANALYZE app.slot_types
   и повторить SQL/браузерный замер. Данные и правила расчёта не меняются;
   план может измениться и для других запросов к справочнику.
2. Если потребуется, отключать JIT только внутри транзакции запроса списка
   аккаунтов, без глобальной настройки БД. Диагностический выигрыш SQL составил
   примерно 12–19 раз. Ускорение полной вкладки после изменения не измерялось.
3. При дальнейшем росте выбирать страницу до обогащения там, где фильтры и
   сортировка это допускают. Проверить все сортировки, поиск, total, подписки,
   архив и слоты на совпадение старых и новых результатов.
4. Сократить 40 дополнительных запросов резервов пакетной загрузкой с теми же
   правами и проверками занятости; не заменять актуальное состояние старым кешем.

## Почему autoanalyze не помог: последующий read-only аудит

По запросу пользователя проверены настройки PostgreSQL 16.14 и статистика
117 пользовательских отношений. Новые ANALYZE, DDL, изменения параметров
или расписаний не выполнялись.

Подтверждено: autovacuum=on, track_counts=on, autovacuum_max_workers=3,
autovacuum_naptime=60s. Порог autoanalyze — 50 + 0,1 × число строк.
Переопределений reloptions у проверенных отношений нет. Автоматический
анализ работает: ui_sections проанализирована 17.11 в 09:26:13 МСК,
supplier_catalog_current — в 09:17:12; у крупных таблиц есть статистика.
В снимке нет обычных таблиц с числом изменений выше порога autoanalyze,
нет транзакций старше пяти минут. Это проверка состояния в момент аудита,
а не гарантия отсутствия будущих задержек обслуживания.

До ручной операции у slot_types было только 6 изменений, 4 строки,
reltuples=-1 и отсутствовала статистика. Шесть изменений не достигают
порога около 50. Время, прошедшее с создания таблицы, само по себе
не запускает autoanalyze. Следовательно, почти неизменяемый справочник
мог оставаться без первоначальной статистики неопределённо долго.
Теперь у него reltuples=4, есть статистика пяти колонок, n_mod_since_analyze=0.
Это соответствует [алгоритму PostgreSQL 16](https://www.postgresql.org/docs/16/routine-vacuuming.html#AUTOVACUUM)
и [настройкам порогов](https://www.postgresql.org/docs/16/runtime-config-autovacuum.html).

Завышенная оценка плана была выше порогов JIT. Рост аккаунтов мог привести
к пересечению этих порогов и резкому замедлению; исторического EXPLAIN,
подтверждающего момент перехода, нет. Для подтверждения текущей причины
достаточны замеры до/после ANALYZE из предыдущего раздела.

### Профилактика, пока не применена

1. Однократно ANALYZE 27 перечисленных таблиц и отдельно finance.entries
   с ограничением ожидания блокировок и времени; затем проверить ключевые
   запросы. Это обновление статистики, а не бизнес-данных.
2. Для slot_types и других редко меняющихся маленьких справочников выбрать
   индивидуальные autovacuum_analyze_threshold=0 и
   autovacuum_analyze_scale_factor=0: тогда поводом для анализа будет хотя бы
   одно изменение. Изменения параметров таблиц оформить новым SQL-файлом
   db/migrations/runtime/ и применять только отдельным согласованным запуском.
   Не распространять эту настройку автоматически на очереди, склад и все
   рабочие таблицы: режим их изменений отличается. Анализ выполняется
   фоновым обработчиком, не синхронно с каждым изменением строки.
3. После первоначального наполнения и восстановления БД явно собирать
   статистику до проверки производительности. В PostgreSQL 16 pg_dump
   [не переносит статистику планировщика](https://www.postgresql.org/docs/16/app-pgdump.html#APP-PGDUMP-NOTES).
   В scripts/sync_prod_to_staging_db.sh после импорта ANALYZE отсутствует;
   это подтверждённый пробел staging-процедуры, не доказательство причины
   первоначального отсутствия статистики в production.
4. Добавить отдельный контроль отсутствующей статистики непустых таблиц,
   длительного превышения порога изменений и статистики родителя finance.entries.
   ANALYZE родителя нужен после начального наполнения и существенного изменения
   распределения данных. Конкретное расписание/интеграцию обслуживания согласовать
   отдельно; во время аудита автоматические задачи не создавались.

Возраст last_analyze сам по себе не повод анализировать неизменившийся
справочник ежедневно. После первоначального исправления важны наличие
статистики и изменения данных. Глобальное отключение JIT или снижение порогов
для всей базы текущими результатами не обоснованы.
