# Контракт CRM ↔ Airpay Hub: airpay.v1

Реализован в исходниках 23.09.2026. Сервисы не переключены и не развёрнуты этой
доработкой; реальные методы поставщика не вызывались. Контракт добавлен к
изолированному Airpay API, основной API Interhub не меняется.

## Согласование версии и исполнителя

`GET /integrations/airpay/contract` требует авторизации, не обращается к
поставщику и возвращает возможности интеграции:

```json
{
  "contract_version": "airpay.v1",
  "provider_code": "airpay",
  "execution_backend": "hub",
  "payments_enabled": false,
  "service_id_type": "string",
  "transaction_id_type": "string",
  "money_type": "decimal_string",
  "max_voucher_quantity": 20,
  "purchase_kinds": ["voucher", "topup"],
  "stock_quantity_available": false,
  "reconcile_uses_pay": true,
  "automatic_pay_retry": false,
  "result_reveal_requires_action": true
}
```

`money_type` описывает суммы журнала/подтверждения покупки; исторический баланс
сохраняет свой текущий числовой формат. `execution_backend` равен `crm` в прямом
режиме и `hub` только в отдельном приложении Hub.

CRM посылает `X-Airpay-Contract: airpay.v1`. Hub возвращает его в ответах Airpay.
Перед каждым внешним POST прокси CRM проверяет GET contract: версию, provider_code
и execution_backend. Несовместимый/старый Hub или прямой CRM вместо Hub не получает
исходный POST. Hub также отклоняет POST без ожидаемой версии до выполнения
обработчика. Прямой режим CRM остаётся совместим с UI без этого заголовка.

Серверные X-Hub-Client/Key и X-Airpay-Owner передаются только внутреннему Hub.
Bearer пользователя CRM не пересылается. Hub разделяет записи по паре
consumer/owner. Несовместимость или недоступность Hub не включает прямой Airpay.
После ошибки POST требуется читать старую операцию, а не создавать новую.

## Операция и результат

Существующие поля UI и маршруты сохраняются. service_id — строка, IDs операций
передаются строками без потери точности JavaScript. preparation_key — стабильный
UUID повторного запроса. Повтор с прежними реквизитами возвращает ту же операцию;
изменение реквизитов с прежним ключом отклоняется. Pay принимает сохранённый ID
и подтверждённую сумму, остальные реквизиты берёт из журнала.

В карточку операции добавлены contract_version, provider_code и следующие поля:

| Состояние | payment_state | result_state | completed |
| --- | --- | --- | --- |
| Подготовка/check | not_started | unavailable для ваучера, not_required для пополнения | false |
| Исход pay неизвестен | processing | unavailable / not_required | false |
| Ваучер оплачен, кода нет | paid | pending | false |
| Ваучер оплачен, код сохранён | paid | ready | true |
| Пополнение подтверждено | paid | not_required | true |
| Подтверждённый отказ оплаты | failed | unavailable / not_required | false |

`result_available` означает наличие сохранённого кода оплаченного ваучера.
`blocks_fallback` снимается только при финальном `failed`; это консервативный
контракт для будущих потребителей, а не включение fallback в CRM или Seller.
Он не заменяет отдельную проверку допуска новой покупки.

Обычная карточка, включая внутренний сериализатор и результат получения ваучера,
не содержит pin_code. Код выдаётся только по POST transactions/{id}/result с
проверкой владельца и аудитом чтения. Pay/reconcile/voucher по-прежнему закрыты
локально; reconcile — повтор исходного pay по явному действию пользователя.

## Проверка старого журнала перед переходом

`GET /integrations/airpay/cutover` доступен только владельцу и возвращает:

```json
{"ready": false, "pending_payments": 0, "missing_vouchers": 1, "active_jobs": 0}
```

Счётчики охватывают всех владельцев старого журнала CRM. missing_vouchers считает
paid-ваучеры без шифротекста и без сохранённого старого текстового кода; оплаченные
пополнения не требуют кода. active_jobs включает все queued/running задания.
В режиме CRM читается его журнал; прокси в режиме Hub также проверяет старую CRM,
а не отправляет этот запрос в новый Hub.

При непустом отчёте CRM блокирует отправку новых prepare/check/pay, а также
check/renew/pay пачки в Hub. Чтение и отдельное завершение уже существующей
операции Hub остаются доступны. Локальный запрет платёжных методов приоритетнее.

Отчёт — диагностика, не атомарное переключение работающих процессов. Перед
переключением требуется завершить старые операции, остановить прямые Airpay
worker и поступление новых действий CRM, повторно проверить отчёт и лишь затем
сменить исполнителя. Нельзя выполнять смешанное развёртывание старого и нового
Airpay API. Interhub при этом не переключается.

## Проверки

Модульные тесты проверяют матрицу состояний, отсутствие кода в карточке,
ограничения владельца, несовместимый Hub и барьер перехода. Межрепозиторные тесты
`api/tests/test_airpay_hub_integration_unittest.py` загружают настоящее ASGI
приложение Hub по AIRPAY_HUB_TEST_SOURCE и связывают его с CRM через TestClient.
Поставщик и БД подменены; серверы и worker не запускаются. Проверяются стабильный
ключ, конфликт реквизитов, разделение оплаты/кода, потеря HTTP-ответа после
сохранённой оплаты, отсутствие повторной покупки, раскрытие и чужой владелец.
При выполненной проверке socket.connect/connect_ex были запрещены целиком.

Фильтры истории и эксплуатационные проверки остаются в
[плане внедрения](airpay-rollout-plan.md).

## Журнал и операторское решение

GET transactions/{id}/events возвращает безопасные события по убыванию ID,
next_cursor используется как before для следующей страницы. Есть аналогичный
маршрут legacy/transactions/{id}/events для чтения архива. События записывает
DB-триггер: обновление без события не коммитится. Реквизиты запросов, raw-ответы
и коды не включаются в JSON события. Аудит раскрытия кода остаётся в отдельной
airpay_result_access. Основание ручного решения доступно владельцу в журнале.

После пяти незавершённых запросов pay или voucher устанавливаются
requires_attention и attention_reason (payment_unconfirmed/voucher_missing).
Автоматический pay не запускается. Старое состояние processing/paid сохраняется;
дальнейшие обращения к поставщику для этой операции заблокированы до разбора.

POST transactions/{id}/resolve принимает request_id (UUID), decision
(confirm_failed/record_success), expected_updated_at, verified=true и evidence
(10–1000 символов). Для record_success нужны provider_transaction_id и код
ваучера в поле code; для пополнения code пустой. Код нельзя дублировать в evidence.
Уже оплаченный ваучер можно дополнить только для прежнего номера оплаты Airpay.
Успех дополняет известную сумму/валюту, не меняя сохранённый запрос pay.

Решение допустимо для processing или paid-ваучера без кода. confirm_failed
никогда не меняет paid. Решение удерживает ту же блокировку, что платёж,
проверяет владельца и updated_at, атомарно сохраняет действие, результат и событие.
Повтор UUID с тем же телом возвращает прежнюю операцию; другой запрос с тем же UUID
отклоняется. Дубликат кода не оставляет ни решения, ни события об успехе.

Этот endpoint меняет только БД и доступен owner даже при выключенных платежах;
он не получает объект транспорта. В архиве CRM resolve не поддерживается.
Сначала нужна реальная внешняя сверка владельцем: кнопка не доказывает исход
у поставщика и не должна использоваться для создания вымышленных покупок.

Для запуска нужны новые runtime-миграции 20260923_05/06. Прямой режим CRM использует
схему app, Hub — supplier_hub_airpay. Подробности внедрения и выполненных проверок
зафиксированы в плане; рабочий контур Interhub не изменён.

## Фильтры истории и Excel

GET transactions и GET transactions/export принимают одинаковые параметры:
- q: до 200 символов, буквальный поиск по ID операции, ID у поставщика, коду
  и названию услуги, аккаунту (знаки % и _ не считаются SQL-шаблоном);
- kind: voucher/topup; status: prepared/checking/check_pending/check_failed/
  checked/processing/paid/failed или completed/awaiting_voucher/requires_attention;
- date_from/date_to: YYYY-MM-DD, даты создания включительно в Europe/Moscow.

completed означает paid с сохранённым кодом либо paid-пополнение;
awaiting_voucher — paid-ваучер без кода; requires_attention — отметка ручного
разбора, независимая от основного состояния. Условия объединяются через AND.

transactions использует limit/offset; export игнорирует пагинацию, возвращает
XLSX до 10 000 строк, при превышении — 422. Суммы и ID хранятся в Excel текстом
для точности. Файл не содержит кодов ваучеров, credentials или сырых запросов/
ответов. Каждая позиция пачки — отдельная строка с номером позиции и UUID группы.
Обычная авторизация owner обязательна. Все методы читают только БД.

В режиме Hub archive=crm обрабатывается локально в CRM для обоих маршрутов.
Он не обращается в Hub; совпадающие ID разных источников не смешиваются.
Новых миграций не требуется; Airpay Hub собирается с requirements-airpay.txt,
который включает openpyxl==3.1.5.

## Восстановление очереди

Контракт объявляет queue_diagnostics=true, queued_job_cancellation=true и
interrupted_payment_job_replay=false. GET queue — только БД и текущий владелец;
POST jobs/{uuid}/cancel — остановка только queued под session advisory lock.
Отмена не меняет состояние покупки. При running/занятом lock ответ 409.
Повтор успешной отмены возвращает то же задание; чужое задание — 404.

GET batches/{id} дополнительно возвращает last_job, если активного job нет,
чтобы ошибка прерванной очереди оставалась видна после открытия истории.
Оба поля задания содержат created_at/updated_at; коды по-прежнему исключаются.
Свободное running pay/voucher/reconcile завершается failed без транспорта.
Подробный порядок восстановления и переключения — [инструкция](airpay-operations.md).
