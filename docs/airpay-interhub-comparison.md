разрывы и план первого этапа «Платежи», находится в

Очередь, переоценка остатка, шифрование/аудит кодов и изолированный модуль Hub уже реализованы: см. актуальное состояние в [airpay.md](airpay.md#долговечная-обработка-и-supplier-hub-реализовано-23092026). Внешние check/pay/получение кода в ходе аудита не выполнялись; проверки оплаты выполнялись только на подменённых объектах, с запрещёнными сетевыми подключениями.

## Где участвует Supplier Hub

Текущие покупки из окна «Платежи» идут так:

```text
Interhub: браузер → CRM /integrations/interhub/* → InterHubService → INTERHUB_API_URL
Airpay:   браузер → CRM /integrations/airpay/*   → AirpayService   → AIRPAY_API_URL
                                                               → AIRPAY_VOUCHER_URL (код)
История Hub: браузер → CRM /integrations/supplier-hub/* → SupplierHubOperatorClient
```

`SupplierHubOperatorClient` умеет только читать историю и раскрывать результат. Вызовов покупки через него здесь нет. История Interhub по умолчанию показывает **Supplier Hub**, отдельный источник «CRM» читает `app.interhub_transactions`. Наличие записи в локальном журнале само по себе не означает появление записи в Hub: в рассмотренном пути оплаты нет отправки туда этой записи. Фактический адрес за `INTERHUB_API_URL` определяется окружением; маршрутизацию production этот аудит не подтверждает.

Отдельно существует **SupplierCatalog** — общий каталог/кэш приложения. Это не транспорт Supplier Hub. В `app.py` в нём и в `VoucherCatalogService` зарегистрирован Interhub; Airpay туда ещё не подключён. Услуги Airpay сейчас доступны только в «Платежах», как и запрошено.

## Сводная

| Область | Interhub | Airpay | Вывод |
| --- | --- | --- | --- |
| Каталог | Услуга → номинал из `value_list` | Отдельная позиция на номинал | Осознанно оставлено по решению пользователя |
| Тип покупки | Тип поставщика (`VOUCHER`, `TOP_UP` и др.) | Фиксированная сумма → ваучер, произвольная → пополнение | Это правило приложения по решению пользователя, не универсальная гарантия протокола |
| Подготовка | Форма под каталогом, динамические поля | Такой же подход; email ваучера по умолчанию `seller@homtech.ru`, редактируется | Совпадает основной сценарий |
| Проверка | `calculate` там, где поддерживается, затем `check`; цена/остаток из отдельных кэшей | `service → prepare → check`; `prepare` сохраняет снимок, `check` получает цену | Разные методы допустимы; оба отделены от покупки |
| Ожидание и подтверждение | Хомяк, модальное подтверждение, отдельная кнопка покупки | Хомяк, модальное подтверждение, отдельная кнопка покупки | Совпадает; визуальную проверку выполняет пользователь |
| Цена | Цена из calculate/check | Для ваучера `fixedPrice`; `finalAmount` не закупочная цена | Сумма и валюта должны браться из одной проверки |
| Остаток | Есть фактический остаток номинала | Количество не предоставляется | Успешный check Airpay не означает резерв или гарантию выдачи |
| Количество | Ваучеры 1–20, отдельная операция на ключ | Ваучеры 1–20, отдельная операция на ключ; пополнение только одно | Общая сумма — сумма цен всех позиций, не увеличение номинала |
| Получение кода | `gift_code` в результате оплаты/статуса | Отдельный вызов после `paid`, `pinCode` сохраняется до возврата | У Airpay «оплачено» и «код получен» — разные состояния результата |
| Неизвестная оплата | `processing`, отдельный `check_status` | `processing`, ручной повтор сохранённого `pay` с прежними ID/датой/телом | Сверка Airpay — платёжный метод; обычное чтение истории его не вызывает |
| Пачка | Фоновый worker, lease, возобновление после перезапуска | Последовательная обработка внутри HTTP-запроса, ручное продолжение | Главное эксплуатационное отличие, см. риски ниже |
| Локальная работа | Существующие ограничения Interhub | prepare/check доступны владельцу; pay/reconcile/выдача кода запрещены | Ограничения Interhub не менялись |
| История | Hub + отдельная история CRM, фильтры/поиск/экспорт | Собственный журнал текущего владельца, страницы, отдельные ключи и просмотр пачки | Нет полной унификации истории и отчётности |
| Сделки/селлеры | Есть связи с deal/Ozon/Yandex и существующие сценарии учёта | Нет связей со сделками, селлером и общим каталогом | Покупку Airpay нельзя считать автоматически учтённой в этих сценариях |

## Хранение и защита от повторов

| Данные / гарантия | Interhub | Airpay |
| --- | --- | --- |
| Журнал | `app.interhub_transactions` | `app.airpay_transactions` |
| Начало записи | Успешный check | До внешнего check, уже на prepare |
| Сумма | `numeric(14,2)` | `numeric(11,2)` на одну операцию; общий итог вычисляется через Decimal |
| Контекст | Услуга, account, params, ответ поставщика, автор | Услуга, account, снимок схемы, исходный запрос, отдельные check/pay/voucher ответы, автор |
| Идентификаторы | ID агента и поставщика | Положительный bigint ID агента, в браузер строкой; ID поставщика; UUID подготовки |
| Перед внешним pay | Сначала сохраняется `processing` | Сначала сохраняются `pay_request` и `processing` |
| Повтор подготовки | По существующей проверенной операции | Уникальный `(created_by, preparation_key)`, прежний ID; изменение реквизитов отклоняется |
| Конкуренция | Условные UPDATE/блокировки, lease пачки | Advisory lock операции и отдельный lock пачки; каждый шаг фиксируется до сети |
| Связь пачки | Отдельная таблица, позиции и уникальный индекс | Детерминированные UUID, служебный `_airpay_batch` в JSON снимка; полнота состава проверяется кодом |
| Сохранённый код | `gift_code` | `pin_code`; ошибка выдачи не откатывает `paid` и не запускает новую оплату |
| Раскрытие | История Hub не содержит код, выдача отдельным действием | Код входит в историю владельца, сырые ответы не выдаются |

Оба локальных журнала содержат коды в текстовых колонках. Это не доказательство шифрования всей БД или резервных копий. Airpay хранит все стадии в одной строке: последние ответы и счётчики, а не отдельный неизменяемый журнал каждой попытки.

## Найденные ограничения и приоритеты

1. **Исправлено в Airpay:** валюта цены в подтверждении бралась из виджета баланса. Теперь приоритет у `purchase_currency` сохранённой проверки. Добавлен тест на расхождение с устаревшим балансом. Текст восстановления теперь прямо объясняет повтор сохранённого запроса оплаты.
2. **До массового использования:** пачка Airpay синхронная. До 20 последовательных check/pay и запросов баланса могут пережить таймаут HTTP-прокси. Обрыв ответа не доказывает остановку серверного цикла. Журнал и блокировки защищают прежние позиции, но пользователь восстанавливает состояние через историю. Нужен отдельный долговечный координатор Airpay с чтением прогресса; автоматический pay/reconcile нельзя включать незаметно. Пока неизвестная оплата останавливает следующие позиции, подтверждённые оплаты повторно не покупаются.
3. **Частичная пачка:** неоплаченные позиции после 15 минут требуют новой подготовки; привязанная переоценка остатка ещё не реализована. Не создавать автоматически новую пачку на всё количество. Сначала восстановить все processing, получить коды оплаченных позиций и определить действительно неоплаченный остаток. Текущий сервер просроченное продолжение отклоняет.
4. **Единый учёт:** Airpay не отражается автоматически в Supplier Hub, общих связках каталога, сделках или селлерах. Для будущего переноса определить один источник истины и одно место выполнения pay. Без этого добавление второй записи/второго исполнителя создаст риск дублей. Перенос Interhub в рамках этой задачи запрещён и не выполнялся.
5. **Результат и доступ:** для соответствия истории Hub полезно отдельно раскрывать код Airpay по действию пользователя и журналировать раскрытие. Сейчас историю видит только owner и только собственные операции. Другой owner не сможет восстановить операцию первого; это нужно учитывать при передаче работы между пользователями.
6. **Правила поставщика:** фиксированная сумма — пользовательское правило определения ваучера. При расширении каталога нужен подтверждённый список исключений/типов; фиксированное пополнение нельзя автоматически отправлять за ваучером. Неизвестный признак сейчас блокирует подготовку. Формат оплаты договоров/квитанций, часовой пояс даты и `ev_* → extras` остаются вопросами к Airpay; сложные схемы оплаты заблокированы. Баланс сейчас проверяется без прибавления overdraft — разрешение кредитного расхода не предполагается.
7. **Проверка конкуренции:** модульные тесты моделируют блокировки и сбои записи, но не заменяют два реальных соединения PostgreSQL. Следующий отдельный этап — проверка конкурирующих запросов и падения процесса на изолированной БД с подменённым поставщиком. Для неё не нужен реальный pay.

Короткий порядок дальнейшей работы: восстановление и прогресс Airpay → переоценка только неоплаченного остатка → единая модель истории/раскрытия → подключение Airpay к целевой архитектуре Supplier Hub. Каждый этап должен сохранять неизменные ID старых операций и не создавать вторую оплату. UI можно унифицировать независимо от методов поставщика; искусственно копировать `check_status` или остатки Interhub нельзя.
