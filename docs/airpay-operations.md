# Airpay: очередь, восстановление и подготовка переключения

Область: только Airpay в «Платежах». Реальные pay, reconcile (повтор pay) и выдачу
ваучера проверяет владелец вручную. Все автоматические тесты используют подмены.
Рабочие API/worker/настройки Interhub не менять.

Пошаговая настройка двух проектов, шаблоны env и порядок первой выкладки:
[Airpay на production](airpay-production-setup.md). Секреты внести до запуска
контейнеров; первый запуск выполняется с выключенной оплатой.

## Что происходит после перезапуска

| Сохранённое задание | Действие нового worker |
| --- | --- |
| queued check/renew | Выполняет прежний запрос с прежними ключами; истёкшая подготовка завершается ошибкой |
| running check/renew, lock свободен | Восстанавливает прежнюю проверку/переоценку; не создаёт повторную покупку |
| queued pay/voucher/reconcile | Начинает только ранее запрошенное действие и только при разрешённой оплате |
| running pay/voucher/reconcile, lock свободен | Останавливает задание с ошибкой 409, не вызывает поставщика и не продолжает оставшиеся позиции |
| Любое задание, lock занят | Пропускает его, включая занятые первые 32 строки; работает с доступными следующими |

Ошибка **задания** не означает отказ **оплаты**. Состояния транзакций, суммы,
ID, коды и оплаченные позиции сохраняются. После остановленного pay сначала
прочитать покупку; при processing нужна внешняя сверка, а не новый заказ.
Если оплачена часть пачки, продолжение оставшихся позиций требует подтверждения.
Если paid без кода — восстанавливать только выдачу оплаченной позиции.

Worker держит session advisory lock до сохранения результата. При штатной
остановке завершённая позиция сохраняется, следующая не начинается. API ждёт
поток не более 5 секунд; при принудительном завершении PostgreSQL освободит
сеансовые locks, а следующий worker применит правила из таблицы.

## Диагностика

В истории Airpay раскрыть «Состояние очереди Airpay». GET
`/integrations/airpay/queue` показывает только задания текущего владельца
(в Hub — пары client/owner): queued, running, отсутствие прогресса более 5 минут,
ожидание разрешения оплаты и ошибки за последние 24 часа. Первые 50 строк
содержат ID покупки/задания, действие, прогресс, даты и наличие DB-lock исполнителя.
Payload, реквизиты, коды и исходные ответы не входят в диагностику.

- running без lock: прежний исполнитель потерян; worker завершит платёжное
  задание без повторного обращения к поставщику, даже при выключенной оплате.
- running с lock, долго нет прогресса: проверить доступность БД/сети и логи Airpay.
  Время без прогресса не доказывает зависание: большой пакет может выполняться долго.
- queued с выключенной оплатой: не включать оплату ради очистки очереди.
  Ненужный запуск можно отменить после подтверждения в панели.
- failed: открыть сохранённую покупку; её финансовое состояние важнее ошибки задания.

POST `/integrations/airpay/jobs/{uuid}/cancel` отменяет только queued под тем же
lock, что worker. Уже захваченное/начатое задание возвращает 409, чужое — 404.
Повтор отмены идемпотентен. Отмена меняет только задание, не транзакцию/платёж.
В архиве CRM панели исполнения и отмены нет.

Опрос прогресса в UI прекращается через 2 минуты; отдельный GET — через 15 секунд.
Это освобождает окно, но не отменяет серверное действие. Позже использовать
«Обновить покупку»; не создавать новый pay из-за таймаута.

Диагностика — снимок БД, а не распределённый heartbeat: она не доказывает,
что worker жив при пустой очереди. `/live` проверяет процесс, `/ready` — конфигурацию
и таблицы. Внешние уведомления/мониторинг подключаются при развёртывании отдельно.

## Перед переключением на Hub

1. Сверить Airpay runtime и manifest, выполнить проверки кода. Для Airpay Hub
   использовать его отдельные Dockerfile, requirements и самостоятельный Compose-проект.
2. **Не менять общий SUPPLIER_HUB_PURCHASES_ENABLED ради Airpay**: он может
   управлять рабочим Interhub. Для предварительного запуска нового Airpay API
   оставить `AIRPAY_PAYMENTS_ENABLED=false` в окружении только Airpay.
3. Завершить/разобрать старые processing и paid без кода. В старом исполнителе
   отменить ненужные queued, дождаться running, проверить весь журнал через
   `GET /integrations/airpay/cutover`: `ready=true` и все три счётчика равны нулю.
4. По отдельному согласованию развернуть миграции и Airpay API Hub. Проверить
   `/live`, `/ready`, контракт, историю/очередь с правильной изоляцией пользователя.
   Поднять только Airpay; не перезапускать существующие api/worker Interhub.
5. Остановить возможность новых прямых операций Airpay в CRM, повторно проверить
   cutover и переключить CRM на `AIRPAY_BACKEND=hub`. Одновременно два исполнителя
   Airpay недопустимы. Окно без новых операций требуется между последней проверкой
   и переключением, поскольку `cutover` — диагностика, а не глобальная блокировка.
6. Проверить подготовку, check, историю, Excel, очередь и архив с выключенным
   Airpay pay. Перед включением ещё раз проверить queued: ранее подтверждённое
   платёжное задание начнётся при разрешении оплаты. Первая реальная покупка —
   отдельная ручная проверка владельца.

При аварии Hub не переключать CRM обратно на прямой pay. Сначала восстановить
Hub/БД/ключ шифрования и прочитать прежние операции. Если нужна смена исполнителя,
сначала доказать отсутствие неопределённых оплат и неоплаченных выдач; не переносить
их через повторную покупку. Резервная копия БД без прежнего ключа шифрования
недостаточна для восстановления кодов.

В этой доработке схема не менялась, миграции не запускались, окружения не
переключались. Проверка PostgreSQL использовала только собственные фикстуры
staging; locks брались до INSERT заданий, чтобы действующий worker их не забрал.

## Защита запуска и комплект поставки (25.09.2026)

CRM собирает Airpay через airpay_bootstrap отдельно и подключает только после
успешной регистрации. Неполная установка или неверный AIRPAY_BACKEND/Hub-конфиг
дают 503 только для Airpay, не останавливают CRM и не включают прямой fallback.
Диагностика пишет только тип исключения, без секретов. Airpay UI загружается
отдельным JS-модулем по выбору поставщика; ошибка загрузки не блокирует Interhub.

Hub docker-compose.airpay.yml теперь самостоятельный проект supplier-hub-airpay.
**Не объединять его с основным docker-compose.yml.** В файле только airpay-api
и airpay-migrate; нет postgres, worker, общих томов и автоматически запускаемых
зависимостей. Существующая Docker-сеть явно указывается как external.
Отдельный AIRPAY_ENV_FILE содержит настройки только Airpay; основной env Interhub
не менять. AIRPAY_PAYMENTS_ENABLED в контейнере принудительно false по умолчанию;
для будущего ручного включения потребуется отдельное явное значение
AIRPAY_DEPLOY_PAYMENTS_ENABLED. Подготовительный preflight разрешает только false.

Пример **не выполненных** команд для выбранного хоста, после проверки резервной
копии, миграций и версии поставки:

```sh
export AIRPAY_ENV_FILE=/absolute/path/to/.env.airpay
export AIRPAY_DOCKER_NETWORK=existing_hub_network
export AIRPAY_RELEASE_TAG=airpay-20260925
export AIRPAY_DEPLOY_PAYMENTS_ENABLED=false
python api/scripts/airpay_deploy_preflight.py
docker compose -f docker-compose.airpay.yml build airpay-api airpay-migrate
docker compose -f docker-compose.airpay.yml run --rm --no-deps airpay-migrate
docker compose -f docker-compose.airpay.yml up -d --no-deps --no-build airpay-api
```

Preflight только читает Compose и существующую сеть, не запускает сервисы.
При неуспехе не выполнять следующие команды. Скрипт не выводит раскрытый env.
Локально Docker отсутствует: реальная сборка образа и проверка Docker-сети
остаются обязательными проверками выбранного хоста, а не считаются выполненными.

Лимиты Airpay: 256 MB/0.5 CPU на контейнер, 16 одновременных запросов API;
подключение к БД 5 секунд, SQL 15 секунд, ожидание SQL-lock 3 секунды.
Это локальные ограничения новых контейнеров/соединений, не настройки Interhub.
Dockerfile.airpay.dockerignore исключает env-файлы, ключи и посторонние каталоги
из контекста сборки. Требуется свободный ресурс на хосте; лимит не резервирует память.

Комплект исходников собирается без изменения git index:

```sh
python api/scripts/build_airpay_release.py --hub /path/to/homtech_hub --output /new/release/directory
```

Скрипт проверяет рабочие модули Interhub относительно HEAD, соответствие runtime
и миграций Airpay, затем включает и tracked, и новые untracked исходники в два
архива с SHA256. Это **наложение на указанные в manifest ревизии**, не команда
развёртывания и не самостоятельный полный checkout. Не распаковывать поверх
боевой рабочей папки; собрать проверочный checkout нужной ревизии и применить
архив там. Совпадение с реально развёрнутой ревизией надо проверить отдельно.
