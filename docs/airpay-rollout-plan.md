## Актуальный ориентир и ближайший шаг (25.09.2026)

Цель — единый логический Supplier Hub: CRM и Seller обращаются к общему
контракту поставщиков, а Hub исполняет запросы через адаптер Interhub или Airpay.
Общими становятся подготовка и подтверждение, идемпотентность, состояния оплаты
и результата, история и аудит. Методы поставщиков остаются внутри адаптеров.
Единый Hub не требует объединять процессы или таблицы: изоляцию Airpay можно
сохранить и в целевом решении.

Последовательность работ:

1. Завершить внедрение Airpay в «Платежах» через Hub: сначала запуск с выключенной
   оплатой и проверка подготовки, истории и восстановления. Реальную покупку
   впоследствии проверяет только пользователь вручную.
2. Отдельными этапами подключить Airpay к сделкам и Seller, используя контракт
   Hub и ссылки на закупку, без второго исполнителя оплаты.
3. Развивать общий интерфейс поставщиков и сводную историю с сохранением
   особенностей их возможностей.
4. Возможный перенос прямых вызовов Interhub из CRM в Hub — отдельный будущий
   проект, только после явного разрешения пользователя и самостоятельной
   регрессионной проверки. Сейчас Interhub не менять ни в одном проекте.

Ближайшая работа — проверка готовности выбранного хоста к изолированному запуску
Airpay: ревизии, отдельный env, Docker/сеть, ресурсы, резервная копия и сохранность
ключа шифрования, точный список миграций. После отдельного разрешения на
развёртывание — миграции Airpay, запуск с AIRPAY_PAYMENTS_ENABLED=false,
проверка контракта/готовности и отсутствия незавершённых операций перед
переключением CRM на Hub. Ручной smoke WorkView выполняет пользователь.

До этого нельзя считать внедрение завершённым: локальные проверки кода пройдены,
но Docker на рабочей машине отсутствует и production-хост не проверен.
Агент не вызывает реальные pay/reconcile или получение ваучера на любом этапе.
Подробности выполненных работ ниже приведены по этапам; их старые формулировки
«следующий шаг» относятся к моменту выполнения соответствующего этапа.

## Выполненный первый шаг: контракт и защита перехода

В коде добавлен [airpay.v1](airpay-contract.md): согласование версии и исполнителя
до POST в Hub, разделение оплаты и готовности результата, отсутствие pin_code в
обычной карточке, диагностика старого журнала и запрет новых действий при
processing/активных заданиях/paid-ваучерах без кода. Пакет Airpay Hub обновлён из
единого исходника. Межрепозиторная цепочка проверена на ASGI-приложениях с
подменёнными БД/поставщиком и запрещённой сетью. Это не завершает этапы B–E:
доработка общей истории и развёртывание впереди.
Изменений схемы БД и переключения окружения в этом шаге нет.

## Второй шаг: события и ручной разбор

Реализован отдельный журнал изменений Airpay: DB-триггер записывает безопасное
событие в той же транзакции, что состояние/попытка/код/замена подготовки. Старые
строки не переписываются. После пяти запросов с незавершённым результатом
pay/voucher выставляется requires_attention, дальнейшие запросы останавливаются.
Состояние processing/paid сохраняется, чтобы не разрешать новую покупку ошибочно.

В карточке доступны журнал и ручное решение: подтвердить отсутствие оплаты либо
сохранить найденный результат. Нужны внешняя сверка, её основание, свежий updated_at
и стабильный UUID решения. Отказ применим только к processing; paid нельзя
отменить. Для ваучера успех требует кода, для пополнения код запрещён. Секрет
шифруется, повтор решения идемпотентен, конфликт кода откатывает всё решение.
Модуль решений не получает транспорт поставщика и не вызывает pay/voucher.

Добавлены миграции 05/06; применены только они к gamesales_staging, checksum и
индекс проверены. Две DB-проверки на своих фикстурах подтвердили блокировки,
откат состояния/события, повторы, шифрование и прежнюю очередь пачек. Реального
поставщика не вызывали. Сеть в 108 серверных тестах CRM и 52 Hub запрещена;
фронт: 674 теста, линтер и сборка пройдены. Staging health — 200, в API нет новых
ошибок; в PostgreSQL одна ожидаемая ошибка тестового дубликата кода. Фикстуры
удалены, подтверждённый staging-туннель закрыт, 5433 свободен.

Согласованный пакет и миграции Airpay доставлены в исходники Hub; его БД и
развёртывание не менялись. Ручной smoke WorkView остаётся за пользователем.

## Решение по первому этапу

Первый этап — корректная ручная покупка Airpay из окна «Платежи» CRM через
Supplier Hub. Сделки, Seller, общая маршрутизация товаров и автовыдача относятся
к следующим этапам. Interhub не изменять в CRM, Hub и Seller: его маршруты,
адаптеры, таблицы, worker и настройки остаются рабочим независимым контуром.

Реальные pay, включая повтор pay при сверке, и получение ваучера выполняет только
пользователь вручную. Агент использует подменённого поставщика; локальные запреты
оплаты и получения кода сохраняются. Production-подключения, миграции и
развёртывание требуют отдельного явного запроса пользователя.

## Итог аудита: что есть сейчас

| Участок | Interhub | Airpay |
| --- | --- | --- |
| CRM «Платежи» | Прямые вызовы поставщика, журнал в CRM | Прямой режим CRM или прокси к отдельному Airpay API Hub; выбор AIRPAY_BACKEND |
| CRM сделки | Прямые покупки, связь со сделкой, код, пересчёт закупочной стоимости | Нет связи операции со сделкой и её себестоимостью |
| Seller | Покупка через основной API Hub, отдельная попытка на единицу заказа, сохранение кода в пул, последующая выдача | Не подключён: клиент, UI и связки ориентированы на Interhub и числовые ID услуг |
| Hub | /v1/purchases, supplier_hub.purchases, очередь, операторская сверка | Отдельное приложение /integrations/airpay/* и схема supplier_hub_airpay; не совместимо с текущим клиентом Seller |
| История CRM | Свой журнал и чтение операторской истории Hub | Свой журнал; при режиме Hub — история модуля и отдельный архив CRM |

Наличие истории Hub в CRM не означает, что CRM покупает Interhub через Hub:
SupplierHubOperatorClient умеет только читать историю и раскрывать сохранённый
результат. Отдельный модуль Airpay уже подготовлен в коде Hub, но это ещё не общий
контракт поставщика для Seller. Его развёртывание не выполнялось в ходе аудита.

У Airpay уже реализованы подготовка и проверка, подтверждение цены, количество
ваучеров 1–20, отдельные ID и записи на каждый ключ, долговечные задания пачек,
защита от повторной оплаты, переоценка неоплаченного остатка, шифрование новых
кодов и аудит раскрытия. Эти механизмы сохраняем и проверяем в маршруте через Hub.

### Конкретные оставшиеся разрывы

1. Контракт основного Hub использует числовой service_id и ожидает код при
   успешной покупке. Airpay имеет строковые ID и различает ваучер и пополнение.
2. На момент аудита проверка переключения CRM → Hub учитывала processing и активные платёжные
   задания, но не paid-ваучеры без сохранённого кода. После переключения старый
   архив не позволяет запросить недостающий код у поставщика. Первый шаг закрыл
   допуск новых операций при наличии таких записей; переход остаётся отдельной
   процедурой после остановки старого исполнителя.
3. Оплата Airpay и получение результата — разные шаги. processing нельзя
   трактовать как отказ; paid без кода нельзя считать готовым товаром.
4. В Seller provider_code покупки жёстко задан как interhub. Выбор связки товара
   не передаёт код поставщика исполнителю. Добавить только запись Airpay нельзя.
5. У Airpay нет связи со сделкой. Interhub пересчитывает purchase_cost по своим
   транзакциям: смешанные покупки в одной сделке без нового решения по учёту
   могут привести к перезаписи стоимости Airpay.
6. Журнал Airpay хранит последние ответы и счётчики, но не полную историю
   переходов и операторских решений; общей операторской истории Hub нет.
7. Тип «фиксированная сумма → ваучер» принят как пользовательское правило,
   а не универсальная гарантия API. Расширение каталога требует проверки типов.

## Целевой маршрут первого этапа

```text
«Платежи» CRM → CRM: авторизация и тонкий API-адаптер
             → Supplier Hub: Airpay API → журнал/очередь Hub → Airpay
«Платежи» CRM ← сохранённые состояние и результат из Hub
```

Hub — единственный исполнитель новых операций Airpay и источник истины по
закупке. CRM не вызывает Airpay напрямую в целевом режиме, не хранит вторую
исполняемую копию покупки и не переключается на прямую оплату при ошибке Hub.
Чтение состояния после таймаута не создаёт новый check/pay.

Изоляция Airpay от Interhub сохраняется. Одинаковый подход не требует одинаковых
таблиц или методов поставщика. На этом этапе фиксируем контракт Airpay,
пригодный для последующего адаптера Seller; существующий /v1/purchases Interhub
и его схему не переделываем. Полная общая история двух поставщиков также не
является условием первой ручной покупки.

## Порядок работ и критерии приёмки

### A. Контракт и единственный исполнитель

- [ ] Зафиксировать версию контракта Airpay: строковый service_id, тип результата,
  владелец/consumer, стабильный ключ операции, сумма и валюта, состояние оплаты,
  состояние выдачи, доступные действия и связь позиций пачки.
- [x] Один ключ с тем же запросом возвращает прежнюю операцию; изменение
  реквизитов с прежним ключом отклоняется. Все тела платёжных запросов заморожены.
- [ ] Подготовка и проверка остаются отдельно от оплаты; оплата требует явного
  подтверждения точной цены и количества. Баланс не гарантирует наличие товара.
- [x] В режиме Hub CRM не регистрирует прямого исполнителя и не делает fallback.
  Поведение при недоступности Hub проверено от браузерного API до журнала.
- [x] Сохранить единый источник исходников Airpay и проверку соответствия
  поставленного runtime; не править копии CRM и Hub независимо друг от друга.

### B. Полный жизненный цикл покупки

- [ ] Подготовка → check → подтверждение → pay → получение кода → сохранённый
  результат работают через Hub для одной позиции и пачки; длительные действия
  не зависят от открытой вкладки или времени ожидания HTTP.
- [ ] Падение до/после отправки pay, потеря ответа и повтор клика не создают
  вторую покупку. Неопределённая оплата блокирует новую оплату и продолжение пачки.
- [ ] Успех оплаты отделён от готовности ваучера. Сбой получения кода повторяет
  только получение кода; пополнение завершается без ожидания ваучера.
- [ ] Уточнение оплаты явно обозначено как платёжный метод: повторяется только
  сохранённый pay с прежним ID, датой и телом, по ручному действию пользователя.
- [ ] Оплаченные позиции не пересоздаются при частичном успехе; новая подготовка
  относится только к разрешённому неоплаченному остатку и требует подтверждения.
- [x] Для зависших операций предусмотрено состояние «требует разбора» и
  защищённое операторское решение с основанием и аудитом. Само решение не
  вызывает pay; отказ можно подтвердить только после внешней сверки.

### C. Хранение, история и UI «Платежей»

- [x] Журнал переходов и попыток реализован в пакете Hub: кто, когда и какое действие
  запросил, IDs, сумма/валюта, итог и ошибка; секреты и коды в события не попадают.
- [ ] Новые коды зашифрованы, обычные ответы их не содержат; раскрытие отдельно
  авторизуется и протоколируется. Резервная копия включает восстановление ключа.
- [ ] История позволяет найти и продолжить одиночную покупку/пачку после
  перезапуска; фильтры и поиск различают оплачено, ожидание кода и неизвестный исход.
- [ ] UI сохраняет подход Interhub: подготовка на странице, хомяк, подтверждение
  количества и итога, прогресс, результат и история. Без имитации остатков Airpay.
- [ ] Для стартового набора услуг проверены тип результата и обязательные поля;
  seller@homtech.ru остаётся редактируемым значением по умолчанию для подходящих
  ваучеров, не подменяет реквизиты пополнения. «Принято от клиента» не возвращается.
- [x] Поиск/экспорт истории Airpay доведены в рамках его экрана. Общий экран Hub
  с Interhub не требуется перед первой покупкой и не меняется в этом этапе.

### D. Безопасное переключение и эксплуатация

- [ ] До переключения проверить все незавершённые оплаты/задания и все оплаченные
  ваучеры без кода. Первый вариант перехода — завершить их у старого исполнителя,
  затем остановить прямые Airpay worker CRM и запретить новые старые операции.
- [ ] Запрет перехода охватывает весь старый журнал, а не только текущего

## Выполнено: восстановление и диагностика очереди (23.09.2026)

- Новый worker не повторяет потерянное running pay/reconcile/voucher: завершает
  только задание, сохраняя состояние и результат покупки. Продолжение — отдельное
  действие владельца. queued остаётся ранее подтверждённым действием и исполняется
  только при разрешённой оплате; безопасные check/renew восстанавливаются.
- Заблокированные первые 32 работы не задерживают следующую доступную. При
  остановке API следующая позиция не начинается; ожидание потока ограничено.
- GET queue показывает свои активные задания и ошибки за 24 часа, прогресс,
  DB-lock исполнителя и причины внимания. Ненужный queued можно отменить с
  подтверждением; lock исключает гонку с worker. Состояние оплаты не меняется.
- История показывает последнее завершённое задание при отсутствии активного.
  Опрос UI ограничен двумя минутами, отдельный GET — 15 секундами; таймаут не
  отменяет задание и не повторяет оплату.
- [Инструкция эксплуатации](airpay-operations.md) описывает восстановление,
  queued при включении оплаты, ограничения диагностики и порядок переключения.
  Общий SUPPLIER_HUB_PURCHASES_ENABLED нельзя менять ради Airpay: он связан с
  работающим Interhub. Для предварительного запуска отключается только Airpay.
- Проверки: 127 тестов backend CRM и 52 Hub с запрещённой сетью; npm run check
  (681 тест, lint, сборка). DB-smoke на staging с собственными защищёнными

## Защита Interhub при внедрении (25.09.2026)

Закрыты выявленные риски на уровне кода и комплекта поставки:

- Сбой настройки/импорта Airpay больше не останавливает общий API CRM. Маршруты
  подключаются атомарно; неудача даёт 503 только Airpay без fallback на прямой pay.
- Интерфейс Airpay загружается отдельным JS-модулем. Проверены отказ Airpay API,
  возврат к Interhub без изменения его баланса/действий и блокировка переключения.
- Compose Airpay превращён в самостоятельный проект только с двумя его сервисами,
  отдельным env и существующей external-сетью. Нет зависимостей, томов PostgreSQL
  или запуска основного worker. Оплата по умолчанию принудительно выключена.
- Ограничены ресурсы новых контейнеров, параллелизм Airpay API и ожидания его SQL.
  Read-only preflight проверяет выбранную Docker-конфигурацию, не выполняя запуск.
- Добавлен сборщик поставки: проверяет неизменность модулей Interhub относительно
  HEAD, согласованность runtime/миграций и включает новые файлы в исходные архивы
  с SHA256. Env-файлы, ключи и дампы не включаются. Git index не меняется.
- Проверки: npm run check — 683 теста, lint, build; 135 backend CRM и 52 Hub —
  с запретом сети. YAML отдельного Compose разобран и проверен локально.
  Существующий WorkInterhubSection и модули Interhub в этом шаге не изменялись.

Это ещё не подтверждение готовности конкретного production-хоста. Docker в
текущем окружении отсутствует, поэтому сборка образа и preflight реальной сети
не выполнены. На выбранном хосте остаются проверки env/ревизий, резервной копии
с ключом шифрования, списка pending migrations, ресурсов и read-only smoke.
Ручной smoke WorkView выполняет пользователь. Реальных покупок, обращений pay,
получения ваучеров, миграций и переключения production в этом шаге не было.
