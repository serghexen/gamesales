# Airpay в окне «Платежи»

Актуальные границы первого релиза, незакрытые сценарии и критерии готовности
зафиксированы в [плане внедрения через Supplier Hub](airpay-rollout-plan.md).
Реализованные ниже механизмы не означают, что переход в Hub и боевой сценарий уже проверены.
Первый шаг этого плана реализован в [контракте airpay.v1](airpay-contract.md):
согласование CRM/Hub, признаки готовности результата и защита перехода.
Второй шаг добавил журнал событий, лимит восстановления и ручные решения
без обращения к поставщику. Миграции 05/06 применены к тестовой БД CRM;
пакет Hub обновлён в исходниках, его развёртывание не выполнялось.

Рядом с Interhub доступны каталог и баланс Airpay, форму подготовки покупки под каталогом, подтверждение цены, история транзакций и сохранённых ваучеров. Оформление использует общий стиль Interhub. Покупка выполняется по цепочке `service → check → подтверждение → pay → получение кода`.

**Локально внешние pay и получение кода запрещены независимо от разрешающего флага.** Вызовы реализованы для серверного режима, но по умолчанию отключены. Реальные pay и выдача ваучера агентом не выполнялись; покупки проверяет только пользователь вручную. По отдельному запросу пользователя 23.09.2026 миграции применены к staging; проверка репозитория выполнена с подменённым Airpay и полным откатом тестовых данных.

## Что уточнила переписка

Источник: пользовательский экспорт «ИП Таран Ю.И - ТОО Airpay», сообщения за июль–август 2026. Доступы и реальные коды из переписки не перенесены в код или документацию.

| Уточнение | Источник | Реализация |

| Код выдаётся отдельным методом после финально успешной оплаты | 863287, 863319–863330 | Отдельный шаг с тем же телом pay и строковым ID агента |

`fixedPrice` принимается в корне ответа или в `displays`. Это поддержка возможного расположения поля, поскольку точного успешного боевого JSON с ним в экспорте нет. Противоречащие друг другу значения блокируют оплату. Для всех фиксированных позиций требуется fixedPrice; один `fixedAmount` не считается подтверждённой закупочной ценой ваучера.

## Настройки

В корневом `.env.dev` реквизиты Basic задаются в `AIRPAY_USERNAME` и `AIRPAY_PASSWORD`, без префикса `VITE_`. Файл исключён из Git. Значения с пробелами и специальными символами заключаются в одинарные кавычки.

- `AIRPAY_API_URL=https://api.airpay.kz/AirPayService/api/v20` — баланс, каталог, параметры, check и pay.
- `AIRPAY_VOUCHER_URL=https://partner.airpay.kz:9969/api/Payment/getVoucherCodeByPaymentId` — полный HTTPS URL отдельного сервиса кода, те же Basic-реквизиты.
- `AIRPAY_PAYMENTS_ENABLED=false` — серверный выключатель pay, повторов pay и получения кода. Включение действует только вне локального режима и при выключенном `GAMESALES_SUPPLIER_OFFLINE`.
- `AIRPAY_TIMEOUT_SEC=20` — таймаут запроса.
- `AIRPAY_SSL_VERIFY=true` — проверка TLS для обоих сервисов; обычный режим работы. `false` явно отключает её, как у Interhub.
- `AIRPAY_CA_CERT_PATH` — необязательный доверенный CA.
- `AIRPAY_PROXY_URL` — необязательный CONNECT-proxy серверного режима, используется обоими сервисами. Сервис ваучеров требует доступа к порту 9969.
- `AIRPAY_TUNNEL_HOST` — локально SSH-хост; пустое значение использует `INTERHUB_TUNNEL_HOST`.
- `AIRPAY_TUNNEL_LOCAL_PORT=3129` — отдельный forward к `api.airpay.kz:443`.

Локально `AIRPAY_PROXY_URL=` и `AIRPAY_TUNNEL_HOST=` можно оставить пустыми. При `GAMESALES_LOCAL_UI=1` разрешённые запросы идут через SSH-forward, без прямого fallback; отдельный локальный туннель к сервису ваучеров не создаётся. Даже `AIRPAY_PAYMENTS_ENABLED=true` не разрешает локальные pay/ваучер.

Задача VS Code `Airpay Tunnel` запускает только этот forward. `Local UI + suppliers (no workers)` объединяет туннели обоих поставщиков, существующий staging-туннель БД, локальные API и UI. Задачи запускает и останавливает пользователь. Конфигурация читается при старте backend; перед его перезапуском сначала выполняется мигратор по правилам проекта.

## Хранение и миграции

Новые файлы:

- `db/migrations/runtime/20260923_01_airpay_transactions.sql` — `app.airpay_transactions`.
- `db/migrations/runtime/20260923_02_airpay_history_index.sql` — индекс истории через `CREATE INDEX CONCURRENTLY`.

Миграции нужны до использования подготовки/истории. Баланс и каталог сами по себе схемы не меняют. Из API не выполняется DDL. Обе миграции применены к gamesales_staging 23.09.2026; проверены записи журнала, таблица, индексы и сценарий подготовки/check/истории с подменённым поставщиком. Production не затрагивался.

Журнал хранит владельца, услугу, аккаунт, выбранный результат покупки, исходный запрос, снимок схемы, ответы check/pay/ваучера, закупочную сумму и валюту, ID Airpay, статус, сроки, счётчики и паузы повторов, полученный pinCode. Сырые ответы и реквизиты остаются в БД; история API возвращает ограниченный набор полей и признак наличия кода. Код раскрывается владельцу только отдельным действием с аудитом. Доступ и резервные копии этой таблицы требуют той же защиты, что и ключи Interhub.

`agentTransactionId` — положительное 63-битное число с первичным ключом в БД; в браузер возвращается строкой для сохранения точности. У подготовки есть отдельный UUID с уникальностью по владельцу: повтор после потери ответа возвращает ту же запись, а попытка изменить реквизиты с этим UUID отклоняется.

Подписанный JWT-снимок живёт 15 минут, используется для check и находится только в памяти формы. Запрос и результат дополнительно сохраняются в БД. Подпись не шифрует реквизиты: токен нельзя публиковать или логировать. Время `agentTransactionDate` сейчас формируется в UTC без смещения, в формате документации; согласованный часовой пояс нужно подтвердить у Airpay.

## Подготовка и доступность

При выборе услуги под таблицей и пагинацией раскрывается форма с прокруткой к ней, как у Interhub. Загружается актуальный `service`; название услуги, поля и кнопка «Получить» расположены в одном блоке. Форма реквизитов остаётся на странице. Во время prepare/check поверх неё показывается общий с Interhub лоадер с хомяком. Успешный check простой схемы сразу открывает компактное окно «Проверьте покупку»: цена, аккаунт, количество и доступность. Курс, ответы поставщика, номер и срок проверки находятся в раскрываемом блоке. Отмена возвращает к форме без оплаты; повторный просмотр итогов не вызывает check. Договоры и квитанции требуют выбора перед открытием итогов. История по-прежнему доступна в отдельном окне. По согласованному правилу приложения `fixed_payment=true` означает ваучер, `false` — пополнение. Ручного выбора типа нет: сервер определяет и сохраняет его по свежему `service`. При неизвестном признаке подготовка недоступна. Для пополнения сумма к зачислению обязательна; для ваучера ручной суммы нет, закупочная цена берётся из `check.fixedPrice`. Поле «Принято от клиента» удалено из форм и результатов; новые запросы интерфейса не передают `amount_from` (внешний `amountFrom`). Сервер сохраняет поддержку этого необязательного параметра для прежних операций. В обоих режимах `account` обязателен, а остальные реквизиты обязательны согласно `inputs.required` поставщика.

Для ваучера поле `account` с подписью Email/«почта» заполняется адресом `seller@homtech.ru` по умолчанию; пользователь может изменить или очистить его. Для пополнений и других видов аккаунта подстановки нет.

Сервер повторно получает service перед подготовкой, проверяет обязательность, regexp и суммы. Регулярные выражения выполняются в отдельном процессе с ограничением времени. Внутренний API принимает суммы строками, внешний JSON отправляет их числами с двумя десятичными знаками.

`check` сохраняется вместе с результатом. Успех требует совпадающего ID агента и ID транзакции поставщика. Для ваучера/фиксированной позиции цена берётся из fixedPrice; для произвольного пополнения — из fixedAmount или проверенной amountTo. `finalAmount`, `rate`, `currencyRate` остаются информацией о конвертации. Валюта закупки читается из баланса агентского счёта и не подставляется по умолчанию. Проверяются депозит и правило amountFrom; перед первым pay баланс читается ещё раз.

UI показывает цену, результат проверки, срок подготовки и отсутствие информации о складском количестве. Успешный check не гарантирует будущую выдачу. `overdraft` отображается как порог отключения приёма платежей, не как дополнительный кредит.

Поля account/identityCard/fullName передаются в корне, остальные — в extras. Снятие префикса `ev_` выведено из примеров services/check и требует подтверждения на нужных услугах. Ответы с договорами/квитанциями можно просмотреть и выбрать, но **их оплата заблокирована**: полного формата вложенных объектов pay нет ни в документации, ни в переписке.

## Оплата, восстановление и ваучер

Первый pay разрешён владельцу только для свежей успешной подготовки и точной подтверждённой цены. Браузер передаёт ID и цену; остальные параметры берутся из БД. Запрос pay и состояние `processing` фиксируются **до** сетевого вызова.

Сессионная advisory-блокировка PostgreSQL сериализует действия одной операции между процессами. Соединение работает в autocommit: фиксация состояния не зависит от завершения сети. После сбоя процесса запись остаётся восстанавливаемой.

Финальный успех — `paid`, подтверждённый отказ — `failed`. Временные коды 1/153/220/255, таймауты, повреждённые ответы, чужие ID, неизвестные коды и 215 остаются `processing`. Код 202 финален при первом обращении; после повтора сохраняется неопределённый статус исходной операции. Успешное состояние нельзя откатить запоздалым повтором.

Отдельного метода статуса в рассмотренной документации нет. «Уточнить результат оплаты» повторяет **сохранённый pay с тем же ID, датой и телом**, как требуют правила уникальности и временных кодов Airpay. Автоматических повторов нет. Серверные паузы: 5, 15, 30, 60, далее 300 секунд. Повторный обычный клик «Купить» для processing отклоняется; сверка запускается отдельно из карточки результата или истории.

После `paid` ваучерная покупка показывает «Получить ваучер». Запрос использует отдельный сервис и то же тело pay, меняя лишь тип `agentTransactionId` на строку. Проверяются ID агента и оплаченной транзакции; pinCode сохраняется до выдачи UI. Следующее получение уже сохранённого кода не вызывает поставщика. Ошибка выдачи кода оставляет оплату успешной и не запускает pay снова. Ошибки HTTP отдельного сервиса отображаются без сырых тел и реквизитов Basic.

Закрытие страницы не удаляет операцию: история читает сохранённые результаты, позволяет вручную уточнить processing и повторить выдачу кода для paid. После потери ответа первоначальной оплаты форма блокирует новую покупку до чтения сохранённого состояния. Фонового опроса и связи со сделками/селлерами пока нет.

## Количество ваучеров

Для ваучера можно выбрать от 1 до 20 ключей; для пополнения количество всегда равно 1. Подготовка создаёт отдельный `agentTransactionId` и строку журнала для каждого ключа. Связь группы хранится в служебном поле `_airpay_batch` существующего JSON `service_snapshot`, поэтому изменения схемы и новые миграции не нужны. В Airpay эти метаданные и количество не передаются. Стабильные UUID подготовки позволяют достроить прерванную пачку без дубликатов.

Проверка последовательно выполняет check для каждого ключа, сохраняет отдельные цены и суммирует их точно. Повтор пропускает уже успешные check. Перед подтверждением проверяется депозит на весь итог; окно показывает количество, цену за ключ (если она одинакова) и общую сумму.

Оплата идёт последовательно с отдельным запросом и сохранением каждого ключа. Пачка имеет собственную advisory-блокировку, а отдельная покупка позиции пачки через одиночный pay запрещена. Временный/неизвестный результат или отказ останавливает последующие оплаты. Повтор пропускает оплаченные позиции; `processing` сначала требует ручной сверки с прежним ID. История позволяет открыть всю группу из любой позиции, прочитать результаты и отдельно подтвердить продолжение неоплаченных ключей. Если срок оставшихся проверок истёк, нужны новые проверки; автоматического создания замены нет.

Получение оплаченных ваучеров выполняется отдельной кнопкой, не вызывает pay и сохраняет каждый код отдельно. Локальные и staging-запреты распространяются на пакетные маршруты. Реальные покупки (`pay`) проверяет только пользователь вручную; автоматические тесты используют подменённый транспорт.

## Внутренние маршруты

Все маршруты требуют Bearer CRM. Чтение баланса/каталога/параметров доступно авторизованному пользователю, остальное — только владельцу. Владелец может заполнять форму и выполнять `prepare`/`check` даже при отключённых покупках в локальном или offline/staging-режиме. Это точечное исключение для предварительной проверки Airpay: `pay`, `reconcile` и получение ваучера остаются запрещены. Чтение истории разрешено; ограничения других поставщиков не меняются.

## Долговечная обработка и Supplier Hub (реализовано 23.09.2026)

Пачки check/pay/получения кодов выполняются отдельным worker. HTTP возвращает
`{job: ...}`, UI опрашивает `GET /integrations/airpay/jobs/{uuid}`. Задание,
прогресс и результат сохраняются в PostgreSQL. Сессионная блокировка не позволяет
двум worker выполнить одно задание. После падения процесса queued/running
задания восстанавливаются по старым ID. Неизвестный результат оплаты остаётся
`processing`: worker не повторяет такой pay автоматически и не покупает следующую
позицию. Явная сверка из истории по-прежнему является платёжным действием.

`POST /batches/{id}/renew` создаёт связанную подготовку только неоплаченного
остатка, в том числе одного ключа. Старые неоплаченные позиции помечаются
заменёнными и больше не принимают pay. Оплаченные и неизвестные операции не
пересоздаются; наличие processing запрещает переоценку. Повтор renew восстанавливает
ту же подготовку. `POST /batches/{id}/check` повторяет сохранённую проверку из
истории с прежними ID; после неё покупку нужно отдельно подтвердить.

Обычная история, check, результат задания и получение ваучера возвращают
`result_available`, без кода. `POST /transactions/{id}/result` читает сохранённый
код и фиксирует просмотр в `app.airpay_result_access`. Это чтение БД, разрешённое
и локально. Новые коды записываются через pgcrypto, их хэш защищён уникальным
индексом, pinCode удаляется из дублирующего сырого voucher_response. Существующие
текстовые коды остаются читаемыми: миграция не переписывает старые данные.
