## Причина и исправление

В диагностике заказа 64209951937 / сделки 27401 / аккаунта 4087 установлено:
старые claims reserve4 и reserve5 от 02.08 повторно запрошены тем же сотрудником
08.11 в 11:32:40 и 11:32:50 МСК. Отдельно reserve8 выдан в 11:32:56 и назначен
сделке в 11:33:08. Причина появилась в `c9c17b1` (production 27.10): список и
назначение исключали из занятых все незакреплённые копирования текущего сотрудника.

- Старые копирования считаются занятыми независимо от сотрудника. Это защищено
  в API списка, копирования и назначения, включая запросы старой вкладки.
- Новая форма генерирует UUID до первого запроса. Повтор после потери ответа
  использует тот же `claim_token`; сервер проверяет аккаунт, код и сотрудника.
- Сохранение скопированного кода требует токен операции. После привязки claim
  погашается, повторное копирование разрешается по сохранённой связи своей сделки.
- Закрытие формы и отмена скопированной сделки не возвращают код в свободные.
- Копирование из карточки аккаунта является самостоятельной выдачей и не делает
  код доступным новой форме сделки автоматически. Для выдачи с сохранением сделки
  нужно копировать из формы сделки. После обновления требуется перезагрузка страницы.
- Механизм постоянных ID не менялся. Новые значения получают номера после
  максимального исторического reserveN и не наследуют занятость удалённых кодов.
  Перестановка сохраняет ID; повторное добавление того же использованного значения
  не делает его новым.

## Ручная проверка пользователем

После обновления страницы на отдельном тестовом аккаунте:

1. Добавить новые значения вместо использованных: новые номера и свободное состояние.
2. Переставить/удалить соседние коды: старые связи не переходят к новым значениям.
3. Открыть новую сделку или дубль: ранее скопированные коды не предлагаются.
4. Скопировать резерв из формы сделки, сохранить и открыть снова: код закреплён,
   повторное копирование своей незавершённой сделки доступно.
5. Отменить сделку после копирования: код не возвращается в подбор новых сделок.
