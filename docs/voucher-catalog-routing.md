# Приоритет поставщиков каталога ваучеров

Настройки относятся к собственному номиналу (`catalog_nominal_id`), а не ко всей услуге.
Один номинал объединяет несколько предложений разных поставщиков. Карточка позволяет
переставлять предложения и отключать их участие в будущей автовыдаче. Селлер пока эти настройки
не использует; покупки и переход на ручную выдачу остаются без изменений.

На основном экране услуга содержит компактные свёрнутые строки номиналов. Строка
показывает количество поставщиков и снимки первого включённого предложения по приоритету;
цены не сравниваются для выбора сводки, остатки разных поставщиков не суммируются.
Стрелка раскрывает поставщиков только выбранного номинала. Название открывает карточку.
Если все предложения выключены, сводка отмечает это и показывает «—» вместо цены и остатка;
сохранённые снимки всех предложений доступны в раскрытых деталях.

## Хранение и чтение

- `voucher_catalog_offers.fulfillment_priority` — положительное число, меньший номер идёт раньше.
- `fulfillment_enabled` — участие в будущей выдаче. По умолчанию `true`.
- `active` по-прежнему означает существующую связку. Отключение выдачи не отвязывает поставщика:
  цена и остаток продолжают обновляться, предложение остаётся видимым в каталоге.
- `voucher_catalog_nominals.fulfillment_revision` — версия настроек и состава связок.

`GET /voucher-catalog` возвращает оба поля предложения и версию номинала. Предложения
внутри номинала идут по `fulfillment_priority`, затем по `offer_id`. Отключённые предложения
сохраняют свою позицию. Пропуски номеров после отвязки допустимы; они не меняют порядок.
При сохранении полного порядка номера нормализуются от 1.

Новая связка добавляется в конец, включённой. Повторное сохранение уже активной связки
сохраняет её приоритет и переключатель. Повторная привязка отвязанного предложения
возвращает его в конец и включает в выдачу. Изменение имени не должно само по себе менять порядок.

## Атомарное сохранение

В существующий `POST /voucher-catalog/items/{item_id}/nominals` добавлено необязательное поле
`routing` у редактируемого номинала:

```json
{
  "nominals": [{
    "catalog_nominal_id": 11,
    "name": "1000 TRY",
    "routing": {
      "revision": 3,
      "offers": [
        {"offer_id": 20, "enabled": true},
        {"offer_id": 10, "enabled": false}
      ]
    }
  }]
}
```

Порядок массива задаёт приоритет. Нужно передавать все активные связки этого номинала,
включая выключенные из автовыдачи. Пустой массив допустим только при отсутствии связок.
Если `routing` отсутствует, текущий порядок сохраняется. Новая `binding`, переданная
вместе с `routing`, добавляется после проверки и сохранения существующего порядка.

Имя, приоритеты, переключатели и новая связка сохраняются в одной транзакции. Все изменения
состава связок используют блокировку родительской услуги и увеличивают версию номинала.
Устаревшая версия, неполный набор или чужие ID дают `409`; дубли ID — `422`.
Ошибка откатывает всю операцию. Редактировать могут только `admin`/`owner` с правом раздела.
Перестановка и переключатели не обращаются к API поставщика.

## Удаление номинала

`DELETE /voucher-catalog/items/{item_id}/nominals/{catalog_nominal_id}` удаляет собственный
номинал и все его предложения (включая ранее отвязанные) одной транзакцией. Родительская
услуга и остальные номиналы сохраняются. В интерфейсе действие доступно через корзину
рядом с названием или из карточки, с отдельным подтверждением. «Отвязать» по-прежнему
касается только одного поставщика.

Удаление разрешено редакторам каталога. Чужой или отсутствующий ID возвращает `404`;
запрет внешнего ключа — `409` с полным откатом операции. Повторно создать номинал с тем
же именем и соответствиями можно; новый номинал получает новый ID. При подключении
селлера его ссылки на номиналы и предложения должны иметь внешние ключи, запрещающие
удаление используемых записей.

## Контракт будущей выдачи

Селлер должен брать активные включённые предложения по сохранённому порядку. Цена не
переставляет поставщиков автоматически. Сохранённый остаток является снимком, а не резервом.
Переход к следующему возможен при отсутствии товара или подтверждённом отказе без покупки.
Таймаут покупки требует проверки её результата у того же поставщика, а не немедленного
повтора у другого. Когда варианты исчерпаны, сохраняется существующий сценарий ручной выдачи.
Этот исполнитель и привязка товаров селлера к собственному номиналу реализуются отдельно.

## Удаление услуги

Корзина в строке услуги и действие «Удалить услугу» в её карточке открывают подтверждение
с сохранённым названием и количеством номиналов. `DELETE /voucher-catalog/items/{item_id}`
доступен администраторам и владельцам с правом просмотра каталога. Под блокировкой услуги
одна транзакция удаляет все предложения (включая отвязанные), затем собственные номиналы
и саму услугу. При конфликте внешнего ключа возвращается 409 и все изменения откатываются.
Другие услуги и каталог поставщика не затрагиваются.

## SKU номинала

Каждый собственный номинал получает постоянный SKU (`HT0000001`, `HT0000002`, …),
общий для всех его поставщиков. При переименовании, изменении приоритетов и связок
код сохраняется. Интерфейс показывает его в строке и карточке номинала, поиск учитывает SKU.
Клиент не задаёт SKU при сохранении: номер выдаёт PostgreSQL, текстовый код вычисляется БД.
После семи цифр номер растёт без обрезания. Удалённые номера не используются повторно;
при откате неудачного сохранения возможны пропуски в последовательности.

Миграции `20260922_01_voucher_catalog_sku.sql` и `20260922_02_voucher_catalog_sku_index.sql`
нужно применить перед обновлением API. Первая присваивает существующим номиналам номера
в порядке `catalog_nominal_id` и задаёт продолжение последовательности; вторая создаёт
уникальный индекс без блокировки обычных записей. Откат версии приложения не требует
удалять присвоенные SKU: добавленные поля совместимы со старым кодом сохранения.


## Собственный склад

Вкладка «Склад» следует за каталогом. Она читает все собственные номиналы с теми же SKU
через `app.voucher_warehouse_stock`: переносить и синхронизировать копии позиций не нужно.
Старые и новые позиции видны даже с пустым запасом. В `app.voucher_warehouse_positions`
хранится одна ручная закупочная цена в рублях для всего пула номинала, с шестью знаками
после запятой. Пустая цена означает «не задана», ноль допустим. Цена не относится к партии.

Владелец открывает «Ключи» напротив SKU и использует ту же форму загрузки, что в селлере:
один код на строку, необязательная дата активации, до 1000 строк за раз. Повторы внутри
пакета и всего склада пропускаются с количеством в результате. Один код нельзя добавить
к двум SKU склада. Существующие пулы маркетплейсов хранятся отдельно, их содержимое
не переносится и не участвует в этой проверке дублей.

Коды шифруются `pgcrypto` с уже используемым `MARKETPLACE_KEY_POOL_SECRET` (минимум
32 символа). Секрет необходимо сохранять вместе с процедурой восстановления, отдельно
от дампа БД. Без него загрузка и раскрытие возвращают 503; обычный список содержит маски.
Полный код виден только после явного раскрытия владельцем. Просмотр сводки использует
отдельное право `voucher-warehouse` (по умолчанию admin/owner); ключи и изменение цены —
только owner, как в существующих пулах селлера.

В карточке сохранённого номинала можно добавить поставщика «Склад»: связка всегда указывает
на этот же SKU. Склад участвует в общем порядке и переключателе включения выдачи. В каталоге
его цена читается из настройки пула, остаток — количество ключей `free` без истёкшего срока
по московской дате; дата активации включительна. Данные пересчитываются при чтении из БД,
без опроса Интерхаба и фоновых задач. Ручная цена не помечается устаревшей по расписанию.

Зарезервированные, передаваемые и выданные ключи не удаляются. Свободные, включая просроченные,
можно удалить с подтверждением. Удаление услуги/номинала, содержащего любые ключи,
блокируется внешним ключом и возвращает 409; вся операция каталога откатывается.
Отвязка поставщика «Склад» не удаляет запас и цену.

### Граничные случаи склада и связок

- Нулевой запас не удаляет связку, не выключает её и не меняет порядок. В карточке и
  сводке показываются `0` и «Нет в наличии». Свёрнутая строка по-прежнему показывает
  первого включённого поставщика по приоритету, даже если у следующего есть запас.
  После пополнения новое количество видно при следующем чтении каталога. Неизвестный
  остаток `—` не считается нулём. Исполнитель селлера пока не подключён.
- Пустой склад без цены можно связать заранее. Уже связанный склад, в том числе
  выключенный или пустой, отмечен «уже связан» и недоступен для повторного выбора.
  Повторный прямой запрос API не создаёт дубль и сохраняет приоритет/переключатель.
  После отвязки повторное добавление возвращает ту же связку в конец включённой;
  ключи, цена и SKU сохраняются.
- Повторная загрузка ключа не меняет его SKU, срок и статус: это относится также к
  зарезервированным, передаваемым, выданным и отключённым ключам. Пробелы по краям
  удаляются, регистр сохраняется. Пустые, слишком длинные и содержащие внутренние
  управляющие символы коды отклоняют весь пакет до записи. Свободный ключ после
  явного удаления можно загрузить заново; удаление занятых ключей запрещено.
- Очистка свободных ключей передаёт `through_key_id` из ответа списка. Сервер
  удаляет только всё ещё свободные ключи этого SKU с ID не больше границы снимка;
  новые поступления из другой вкладки сохраняются. Без положительной границы API
  отвечает 422. Счётчики, граница и страница читаются в одной транзакции REPEATABLE READ.
- Двойное нажатие сохранения не отправляет второй запрос из формы. Устаревшие
  приоритеты или изменившийся состав связок дают 409 с откатом всей транзакции.
  Поздний ответ предпросмотра не восстанавливает отменённую связку и не подменяет
  выбранного поставщика.
- Ручная цена пула сохраняется с обязательным `expected_updated_at` (null при
  первом сохранении). Под блокировкой номинала сервер сверяет версию и возвращает
  409 при конфликте. Форма перечитывает актуальную цену, сохраняя ввод. Повторная
  попытка показывает обе цены и требует подтверждения замены; отказ принимает
  свежую серверную цену. Это относится также к нулю и очистке цены.

Перед запуском новой версии API применить миграции до `20260922_04_voucher_warehouse_index.sql`
включительно (SKU — 01/02, склад — 03/04). Новые таблицы, представление, поставщик и права
создаются только мигратором. Изменения не включают списание, резервирование и исполнение
заказов селлера: будущий исполнитель должен атомарно резервировать свободный непросроченный
ключ по SKU, сохранять связь с заказом и исключать повторную выдачу.
